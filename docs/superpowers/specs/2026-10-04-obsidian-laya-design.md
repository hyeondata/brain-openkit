# Brain OpenKit — Laya 기반 Obsidian 지식 관리 도구 설계 초안

작성일: 2026-10-04
상태: 최초 CLI alpha 구현 완료. 아래는 확장 방향을 포함한 설계이며, 실제 구현 범위와 검증 결과는 [구현 기록](../../implementation-notes.md)을 기준으로 한다.

프로젝트 표시명은 **Brain OpenKit**, 저장소와 CLI 명칭은 `brain-openkit`으로 확정했다.

[이름과 공개 배포 구상](../../project-identity.md)을 함께 참고한다.

## 1. 목표와 현재 합의

사용자는 claude-obsidian의 노트 정리·검색 방식을 참고해 구현하려고 한다. 판단 작업에 생성형 모델을 매번 호출하는 대신 Laya를 기본으로 사용하고, 추후 API 키를 넣어 Jev로 교체할 수 있어야 한다.

첫 단계의 목표는 한국어·영어 Markdown 노트를 검색하고, 관련 노트와 분류 후보를 근거와 함께 제시하는 것이다. 추천 품질과 실제 로컬 실행 비용을 확인한 뒤 파일 반영과 위키 생성으로 확장한다.

현재 저장소에는 Python CLI와 합성 예제 노트가 있다. 실제 vault 경로는 실행할 때 사용자가 지정한다. 원본 프로젝트의 코드를 복사하지 않고 검색·원문 보존·실패 복구 방식을 참고해 독립 구현했다.

사용자는 첫 인터페이스로 로컬 CLI를 선택했다. 검색·판단 코어는 추후 Obsidian 플러그인 또는 로컬 웹 화면에서도 재사용할 수 있도록 분리한다.

## 2. 접근 방식 비교

| 방식 | 장점 | 부담 | 판단 |
| --- | --- | --- | --- |
| Python 코어 + Laya 로컬 HTTP 서버 + CLI | 모델 서버와 앱 분리, Jev로 전환 용이, 검색 평가가 간단 | 앱과 모델 서버를 각각 실행 | 첫 단계 추천 |
| Python 앱에 Laya 모델 직접 로드 | 별도 서버 없이 실행 | 모델 의존성·메모리·초기 로딩이 앱에 결합 | 단일 실행 파일이 우선일 때 재검토 |
| Obsidian 플러그인부터 구현 | 실제 노트 작업 흐름에 바로 연결 | 화면·플러그인 배포와 모델 연동을 동시에 검증 | 코어 검증 뒤 확장 권장 |

## 3. 첫 버전 범위

### 포함

1. 지정한 vault의 Markdown 파일을 읽고 로컬 검색 인덱스를 만든다.
2. 질문에 대한 후보 문단을 BM25로 검색한다.
3. Laya가 각 후보와 질문의 관련성을 판단하고 결과를 다시 정렬한다.
4. 사용자가 제공한 분류 목록에서 노트의 분류를 추천한다. 태그는 각각 독립적인 적용 여부로 판단하므로 여러 개를 추천할 수 있다.
5. 파일 경로, 제목, 실제 원문 발췌, 문단 위치, 판단 결과를 텍스트 또는 JSON으로 출력한다.
6. 모델 연결 확인과 소규모 품질 평가를 제공한다.

### 후속 단계

- 승인한 추천을 frontmatter와 링크에 반영한다.
- 원문 출처를 유지하며 자료를 수집하고 위키를 생성한다.
- 요약·종합·새 글 작성에 필요한 생성형 모델을 별도로 연결한다.
- Obsidian 플러그인 또는 웹 화면을 추가한다.

첫 버전에서 분류·태그는 추천 결과로 제공한다. 링크 추천, 자동 파일 이동이나 원문 변경 기능은 후속 단계에서 반영 이력 및 되돌리기와 함께 설계한다. Laya와 Jev는 자유 형식의 요약문을 작성하는 역할을 맡지 않는다.

## 4. 구성과 데이터 흐름

```text
CLI / 추후 UI
   │
   ├─ VaultReader → Chunker → SQLite 인덱스 → BM25 후보 검색
   │                                             │
   └─ 검색·분류 워크플로 → DecisionProvider ← 후보·노트 발췌
                               ├─ LayaProvider → 로컬 Laya HTTP 서버
                               └─ JevProvider → TypeSafe API (후속 구현)
                                    │
                              응답 검증·결과 구성
                                    │
                     원문 경로·발췌·추천 + 실행 정보
```

- `VaultReader`: UTF-8 Markdown 읽기, vault 상대 경로 생성. `.obsidian`, `.git`, 앱 캐시와 vault 밖으로 연결된 심볼릭 링크는 제외한다.
- `Chunker`: 제목과 문단 경계를 우선하여 분할하고 원문 줄 번호와 내용을 보존한다. 제목·경로는 검색 정보로 사용한다.
- `Index`: 파일 내용 해시로 변경을 감지한다. 수정·삭제한 노트의 오래된 문단을 제거하고 갱신한다. 캐시는 프로젝트의 `.cache/` 아래에 vault별로 분리한다.
- `Retriever`: BM25 검색을 수행한다. 초기 한국어 처리는 정규화한 단어와 한글 문자 2-gram을 함께 사용하는 접근을 평가한다. 형태소 검색 또는 임베딩 검색 도입은 실제 검색 실패 사례를 보고 결정한다.
- `Workflow`: 검색 후보 구성, 분류 질문 작성, 판단 결과 정렬을 담당한다.
- `DecisionProvider`: 판단 요청과 응답의 공통 계약이다. HTTP 전송과 제공자별 모델 설정은 어댑터에서 처리한다.
- `Presenter`: 화면 출력과 JSON 출력을 담당한다. 근거는 원문 발췌로 제시하며 모델이 쓴 설명으로 대체하지 않는다.

## 5. 제공자를 교체하는 계약

공통 요청은 다음 의미를 갖는다.

현재 alpha는 `choose(state, question, choices)`와 choice 응답만 구현했다. 아래의 여러 질문 묶음, score/noul은 확장 계약이다.

- `state`: 판단에 필요한 텍스트 또는 구조화한 텍스트 필드.
- `questions`: 이름을 붙인 choice / score / noul 질문.
- 질문의 선택지와 기준은 워크플로가 작성한다.
- 제공자, 서버 주소, 인증, 모델 이름, 입력 예산, 시간 제한은 제공자 설정으로 전달한다.

공통 응답은 다음을 보존한다.

- 질문별 선택·점수·참 확률과 선택지 확률 분포.
- 제공자 이름, 실제 사용 모델, 소요 시간, 사용량.
- 제공자가 반환한 신뢰도 수치와 그 의미. 없는 값은 null로 둔다.
- 입력 축약 여부와 사용한 원문 발췌 범위.

응답의 필수 필드, 선택지 포함 여부, 유한한 수치, 확률 범위를 검증한다. 잘못된 응답은 판단 실패로 처리한다.

공통 형식을 사용해도 제공자 간 확률 보정이나 신뢰도 동등성을 가정하지 않는다. 신뢰도 임계값은 제공자·작업·선택지 수를 함께 고려해 검증한 설정으로 관리한다. 임의의 공통 임계값으로 파일 반영을 결정하지 않는다.

첫 구현은 LayaProvider를 완성하고 공통 계약을 검증한다. JevProvider는 그 계약에 맞춰 추가할 수 있도록 구성하되, 첫 단계에서 Jev 연결이 구현·검증되었다고 표시하지 않는다.

## 6. Laya 설정과 실행

- 공식 Python `laya[serve]` 패키지를 별도 가상 환경에서 실행한다.
- 서버는 `LAYA_HOST=127.0.0.1`로 설정한다. 앱 기본 주소는 `http://127.0.0.1:8000`이다.
- 앱은 `POST /v1/systemone`으로 요청한다.
- 모델은 명시적으로 `multilingual`을 사용한다. 서버도 다국어 체크포인트만 적재하도록 설정해 영어 모델의 추가 로딩을 줄인다.
- 실행 장치는 별도 서버의 환경 변수로 설정한다. 검증한 README 예시는 CPU를 사용하며 MPS는 별도 검증이 필요하다. 서버가 제공하는 상태는 `doctor`에서 확인한다.
- 입력 한도는 명시적으로 설정한다. 최대 8,192토큰 지원을 활용하되, 전체 vault나 여러 긴 노트를 한 요청에 넣지 않는다.
- 관련성 판단은 질문과 후보 문단 한 쌍을 하나의 state로 보낸다. 많은 문서 ID를 하나의 선택 문제로 넣지 않는다.
- 선택 문제는 초기 최대 10개 후보로 제한한다. 그보다 큰 분류 체계는 후보를 좁힌 뒤 판단한다.
- 현재 alpha는 요청 바이트 크기를 먼저 제한하고, 서버가 반환한 토큰 잘림·질문 잘림·선택지 붕괴를 거절한다. 클라이언트에서 제공자 토크나이저로 미리 계산하는 기능과 자동 재분할은 후속 단계다. 잘림 감지 시 검색은 BM25로 돌아가며 분류는 명시적으로 실패한다.
- 첫 실행은 모델 다운로드와 초기 로딩이 필요하다. README와 진단 결과에서 최초 실행과 이후 실행을 구분한다.
- 모델 revision과 패키지 버전을 평가 결과에 기록한다. 구현 시 확인한 버전을 고정해 같은 조건으로 재평가할 수 있게 한다.

HTTP 서버 방식은 제공자 교체를 간단하게 하기 위한 선택이다. 앱이 Laya 모델의 내부 구현이나 학습 코드에 의존하지 않게 한다.

## 7. 검색 흐름

1. 검색 문자열을 정규화하고 로컬 인덱스에서 BM25 상위 20개 문단을 찾는다.
2. 검색 결과가 없으면 빈 결과를 반환한다. 검색 실패를 모델이 보충하도록 요청하지 않는다.
3. 각 후보에 대해 질문과 원문 발췌를 입력하고 관련/무관의 두 선택지로 판단한다. 키는 `A`/`B`, 설명은 의미가 드러나는 문장으로 작성한다.
4. 관련 선택지의 확률을 정렬 신호로 사용한다. 이것이 객관적 관련성 또는 보정된 확률이라고 표시하지 않는다.
5. 동일 노트의 문단을 묶고 상위 5개 노트를 반환한다. 동률은 BM25 점수와 경로 순으로 결정한다.
6. 파일 경로, 줄 번호, 원문 발췌, 검색·모델 점수를 함께 제공한다.

모델 서버 연결 실패 시 BM25 검색 결과는 제공할 수 있다. 이때 `rerank_status=unavailable`을 표시하고, Laya가 판단했다고 표시하지 않는다. 설정된 Laya 요청을 Jev로 자동 전송하는 동작은 기본으로 두지 않는다.

## 8. 분류·태그 추천 흐름

1. 사용자가 분류명과 설명, 태그명과 설명을 설정한다.
2. 노트 제목·메타데이터와 본문 문단을 읽는다.
3. 분류는 최대 10개 선택지와 지정된 예산 안에서 판단한다. 장문은 분할한 결과를 보여주고, 문단 간 분류가 충돌하면 검토 필요로 표시한다.
4. 태그마다 적용/미적용의 두 선택지 판단을 수행한다. 여러 태그가 동시에 적용될 수 있다.
5. 각 추천의 입력 발췌와 확률을 출력한다. 태그는 적용 선택지가 가장 높은 경우 적용 후보로 표시하되, 확률과 미적용 결과도 확인할 수 있게 한다. 장문 여러 조각의 확률을 합쳐 보정된 문서 전체 확률처럼 표시하지 않는다.

첫 버전의 기준은 사용자가 정한 기존 분류·태그다. 모델이 새로운 태그명을 생성하는 기능은 범위에 포함하지 않는다.

## 9. 설정과 사용 흐름

설정 파일에는 제공자 선택, 서버 주소, 모델, vault 경로, 후보 수, 출력 형식을 둔다. API 키는 설정 파일에 직접 넣지 않고 제공자별 환경 변수에서 읽는다.

| 설정 | Laya 기본값 / 규칙 | Jev 연결 시 |
| --- | --- | --- |
| provider | laya | jev |
| base_url | http://127.0.0.1:8000 | https://api.typesafe.ai |
| model | multilingual | jev-latest 또는 버전 고정 |
| 인증 | LAYA_API_KEY, 서버 인증을 설정한 경우만 | TYPESAFE_API_KEY 필수 |
| 입력·선택지 예산 | Laya 모델과 질문 예산으로 검증 | Jev 제한으로 검증 |

구현한 CLI 명령은 아래와 같다. 현재 `search`와 `evaluate`의 기본 제공자는 `none`(BM25)이며, `--provider laya`로 재정렬을 선택한다. 모델은 `multilingual`로 고정한다. 현재 설정 파일의 실제 키와 실행 옵션은 [README](../../../README.ko.md)를 참고한다.

```text
brain-openkit doctor
brain-openkit index --vault /path/to/vault
brain-openkit search "질문" --vault /path/to/vault
brain-openkit classify /path/to/vault/note.md --taxonomy taxonomy.json
brain-openkit evaluate evaluation.jsonl --vault /path/to/vault
```

`doctor`는 설정과 서버 연결을 확인한다. 실제 모델 추론 확인은 별도 옵션으로 실행해, 단순 연결 확인이 모델을 불필요하게 다운로드하지 않게 한다.

## 10. 오류 처리와 검증

- 파일 읽기 오류는 해당 경로와 함께 보고하고, 인덱싱 성공·실패 수를 구분한다.
- HTTP 401은 인증 설정 오류로 즉시 반환한다. 422는 요청 문제로 반환한다. 일시적 연결·서버 오류만 횟수를 제한해 재시도한다.
- 응답 내용과 노트 원문을 기본 로그에 남기지 않는다. 인증 값은 출력하지 않는다.
- 단위 테스트는 입력 예산 초과, 응답 형식 오류, 수정·삭제 인덱스 갱신 등 실패 경계를 검증한다.
- 임시 샘플 vault와 모의 HTTP 서버로 경로·줄 번호·실패 시 BM25 결과 유지·설정별 인증 전송을 검증한다.
- 실제 Laya 실행 테스트는 별도로 수행한다. 모의 서버 테스트 통과를 모델 품질 검증으로 보고하지 않는다.

실제 한국어 평가 자료는 사용자가 검토한 정답을 사용한다. 검색 질문과 정답 노트 30개 이상, 분류·태그 예제 50개 이상으로 초기 비교를 제안한다. 이것은 소규모 도입 판단 자료이며 일반적 품질 보증이 아니다.

검색은 BM25 단독 대비 recall@5와 MRR을 비교한다. 분류·태그는 정확도와 precision/recall을 기록한다. 질문·선택지 문구 수정에 사용한 자료와 최종 평가 자료를 분리한다. 모델 추론의 첫 실행 시간과 이후 실행 시간을 따로 기록한다. 검색 품질이 개선되지 않으면 Laya 재정렬을 기본으로 활성화하지 않는다.

## 11. 완료 기준과 확장 순서

첫 단계 완료 기준:

- 샘플 vault를 인덱싱하고 출처가 확인되는 검색 결과를 출력한다.
- Laya 다국어 모델에 실제 요청을 보내 검색 재정렬과 분류 추천을 실행한다.
- 모델 실패와 기본 검색 결과를 구분해서 표시한다.
- 제공자 계약 테스트가 통과하고 Jev 추가 시 바꿀 부분이 어댑터와 설정으로 제한된다.
- 실제 모델 테스트와 품질 평가의 결과·제약을 보고한다.
- 설치·서버 실행·CLI 사용·평가 절차를 README로 재현할 수 있다.

확장 순서는 Jev 어댑터 → 추천 반영과 되돌리기 → 자료 수집·위키 생성 및 생성형 모델 연결 → Obsidian 플러그인 또는 웹 화면으로 제안한다.
